0. 结论先行

一个科研项目就是一个持续数天、数月、有固定科学流程的长期执行任务。项目应该有一个项目级“大工作流”，并且这个大工作流直接对齐前端已经确定的标签栏：

项目概述 -> 相关工作调研 -> 实验实现 -> 学术论文撰写

层级规则：

  • 一级：项目概述、相关工作调研、实验实现、学术论文撰写，对应前端第一栏。
  • 二级：每个一级区域内部的工作区，对应前端第二栏。
  • 三级：每个二级工作区内部的具体页面，对应前端第三栏，也是最小的叶子工作流。

不要把整个项目实现成一条永不结束的线性步骤链，而是实现成一个持久化的项目级执行图。这个大执行图只负责：

  • 定义一级、二级、三级之间的依赖和条件分支；
  • 在可以并行的节点（例如多个实验、多个论文章节）上 fan-out / fan-in；
  • 等待审批、等待实验结果、等待外部服务时持久化休眠；
  • 在事件到达时重新计算哪些节点可以执行；
  • 在项目总览页面显示整张执行图。

换句话说：整张图中的所有节点共同构成一个项目级大工作流；浅色阴影框表示其中某一个子工作流；每个叶子节点本身也可以再展开为一个更小的 Mastra 工作流。

1.2 单次意见与多轮对话的适用场景

判断标准不是“在哪个页面”，而是“这次交互能不能一次说完，还是需要先看到中间结果再继续”。同一个页面往往同时存在单次和多轮入口。

场景 类型 说明
新建项目的 Idea 澄清 多轮 逐步收敛研究问题、假设、范围、边界和成功标准
项目规格与研究问题细化 多轮 需要反复澄清范围和验收条件
文献与相关工作讨论 多轮 查看文献候选、研究现状矩阵和引用图后讨论是否纳入、缺口和证据关系
方法设计与代码实现讨论 多轮 讨论方法方案、实现策略、执行约束
实验规划 多轮 设计实验矩阵、数据集、指标、随机种子和执行条件
实验结果解读 多轮 查看指标、Artifact 和谱系后询问原因、决定是否继续或补充实验
论文写作指导 多轮 大纲、章节、引用、图表、实验数据选择和审阅意见
项目日常监督咨询 多轮 全局 ProjectChat 可以针对任何工作流状态提问和讨论
批准/拒绝 Proposal 单次 一次明确决策即可，例如批准实验、拒绝方法修改

单次意见和多轮对话只是第一层分类，未来可以继续扩展更具体的反馈类型。每种反馈都应记录 project_id、来源对话、关联节点和它触发的新工作流；定期总结则独立保存为一份只读报告，并允许用户从总结里直接发起单次意见。

2. 第二层：运行模型

2.1 为什么不能做成一条永不结束的步骤链

start -> overview -> related_work -> implementation -> paper -> done

这条链只能表达“顺序”，表达不了：

  • 五个实验同时跑；
  • 论文多个章节同时撰写；
  • 等待实验结果、等待审批、等待外部服务；
  • 定期总结按配置的时间间隔自动触发但不阻塞主线；
  • 暂停、恢复、取消和部分失败；
  • 服务重启后恢复长期项目。

因此运行时采用事件驱动的持久化调度器，而不是线性阻塞执行器。

2.2 节点状态机

stateDiagram-v2
    [*] --> pending
    pending --> ready: 依赖满足且条件成立
    ready --> running: 调度器领取并启动
    running --> waiting_human: 进入审批/用户确认
    running --> waiting_resource: 等待实验/外部服务/artifact
    waiting_resource --> running: 事件到达并恢复
    waiting_human --> running: 用户批准/拒绝后恢复
    running --> succeeded: 执行成功
    running --> partial: 子节点部分成功
    running --> failed: 执行失败且不可自动恢复
    running --> cancelled: 用户取消或项目取消
    partial --> ready: 满足继续条件
    failed --> blocked: 需要人工干预
    blocked --> ready: 用户修订后重新调度
    succeeded --> [*]
    cancelled --> [*]

项目本身还有一层全局状态：

active / paused / cancelled / finished

暂停不是“杀死一切”，而是：

  • 不再调度新的 ready 节点；
  • 已经在运行的实验可以安全跑到检查点，或者由用户选择取消；
  • 所有未完成节点保持可恢复状态；
  • 恢复时调度器重新计算哪些节点满足条件。

2.3 调度器如何不空转

事件源：
  节点完成
  审批通过/拒绝
  实验完成/失败/取消
  相关工作任务完成
  定时任务（定期总结）
  用户手动触发（暂停、恢复、重试、跳过）
        |
        v
  调度器 tick
        |
        v
  读取执行图，计算 ready 节点
        |
        v
  在项目级/全局并发配额内派发到 worker 池
        |
        v
  每个子工作流持有 mastra_run_id / correlation_id
        |
        v
  完成事件写回 PGlite，继续下一轮 tick

当没有 ready 节点且没有运行中的节点时，调度器只是“睡着”，不会调用大模型，也不会占住 worker。

3.2 与现有代码的差距

当前项目已经有一些 Mastra workflow，但它们目前是零散的薄封装，而不是项目级总编排：

当前实现 未来的角色
research-bootstrap（文献搜索 + 证据覆盖评估） 相关工作调研 区域中的子工作流
proposal-approval-gate（suspend/resume） 审批节点，挂在任何高风险子工作流前面
supervision-reports（当前报告机制） PeriodicReportWorkflow：项目概述 中的旁路子工作流
project-chat Idea 讨论 / 反馈协调节点
task-worker（当前全局 working 串行） 改为多 worker 并发池
原生实验监督器 本方法实现 中每个实验叶子节点的执行后端

目前代码里的主要差距：

  • task-worker.ts 用全局 working 标志，一次只处理一个任务，真实执行是串行的；
  • Mastra workflow 大多只是调用服务器 API 的薄包装，没有项目级依赖图；
  • 报告 workflow 在一个 step 中顺序遍历所有项目，一个项目失败可能影响整批报告；
  • 实验、复现运行和审批各有自己的状态表，但没有统一的项目执行图投影；
  • Mastra Studio 的 workflow graph 只展示单个 workflow 的技术步骤，不能直接展示跨区域、跨实验、跨 Proposal 的项目总览。

所以项目总览页需要一张业务级执行图，它把四个一级区域、二级工作区、三级页面、Mastra run、实验、Proposal、报告和 Artifact 状态聚合到同一个图上。

4. 第四层：数据模型与关键设计

4.1 核心表

建议在 PGlite 中新增：

project_executions
  id, project_id, definition_version, status,
  policy, created_at, started_at, paused_at, finished_at

workflow_nodes
  id, execution_id, parent_node_id, node_key, node_type,
  area, group_key, tab_key, workflow_key, status,
  input, output, attempts, error, started_at, finished_at

workflow_edges
  id, execution_id, from_node_id, to_node_id,
  condition, priority

workflow_events
  id, execution_id, node_id, event_type,
  payload, created_at

节点上的 area / group_key / tab_key 直接对应前端一级、二级、三级导航，让执行图可以按标签栏渲染。

每个节点还保存关联信息：

project_id
parent_run_id
correlation_id
mastra_run_id（如果有）
proposal_id（如果是审批节点）
experiment_id / reproduction_run_id（如果是执行节点）

这样业务状态和 Mastra checkpoint 可以互相追踪，服务重启后也能恢复。

4.2 节点类型

节点类型 作用
action 调用一个 Mastra workflow 或服务器 API
composite 一个包含子图的二级/三级子工作流
fork fan-out，把多个并行子节点同时派出
join fan-in，按策略（全部/部分/阈值）汇聚结果
condition 根据上游结果选择后续路径
approval 等待用户审批，产生 Proposal
wait 等待外部事件，例如实验完成或定时器
report 生成定期总结等旁路产物
interaction 需要用户输入或确认，例如 Idea 讨论、用户反馈、审批
presentation 把进度、报告、结果或决策请求呈现给用户

4.3 并行与失败策略

  • 实验矩阵使用 fork 并行启动多个实验；
  • 每个实验节点内部是：Proposal 审批 -> 执行 -> Artifact 验收；
  • 论文撰写使用 fork 并行撰写章节，再 join 合并；
  • join 支持三种策略：
    • all：全部成功才继续；
    • threshold：达到最少成功数即可继续，其余标记为 partial；
    • any：任一成功即可继续；
  • 默认建议 threshold，因为科研中部分实验失败后可以修订方法，而不是让整个项目失败；
  • 论文章节并行写入时需要版本锁定、引用 provenance 和最终合并校验。

4.4 暂停、恢复、取消

  • 暂停：设置项目级 paused，调度器停止派发新节点；
  • 恢复：设置 active，调度器重新计算 ready 节点；
  • 取消：只允许取消尚未终态的节点，已完成的实验/Artifact 保留审计记录；
  • 审批节点被暂停时保持 waiting_human，恢复后仍可继续审批。

5. 第五层：实施步骤

Phase 0：执行图数据模型与事件日志

  • 新增 project_executions、workflow_nodes、workflow_edges、workflow_events；
  • 节点保存 area / group_key / tab_key，保证与前端导航一一对应；
  • 定义节点状态、条件边和并发策略的 Zod 契约；
  • 为现有 tasks、experiments、reproduction_runs、proposals 补充 execution_node_id / correlation_id。

Phase 1：项目总览执行图（先做用户能看到的）

  • 实现 /api/projects/:projectId/execution-graph，返回一级、二级、三级节点、边和状态；
  • 在 项目概述 -> 进度与待决策 或 Overview 主区域渲染这一张巨型执行图；
  • 支持点击节点查看子工作流、Mastra run、实验、审批详情；
  • 支持空状态、失败状态、暂停状态和窄屏布局。

Phase 2：事件调度器与多 worker

  • 把 task-worker.ts 的全局 working 换成并发 worker 池；
  • 支持按项目和全局配置最大并发数；
  • 调度器在 tick 中只派发 ready 节点；
  • 服务重启时恢复未完成的节点，而不是把运行中的实验直接标成失败。

Phase 3：把现有 workflow 包装成子工作流

  • RelatedWorkWorkflow、EvidenceWorkflow、ApprovalWorkflow、PeriodicReportWorkflow、UserFeedbackWorkflow；
  • PeriodicReportWorkflow 按项目配置的时间间隔自动汇总当前执行图状态，并保存为只读报告；
  • UserFeedbackWorkflow 区分单次意见和多轮对话：单次意见直接转为 Proposal 或新节点，多轮对话绑定持续会话；
  • 每个子工作流保留 project_id、parent_run_id、node_id、correlation_id；
  • Mastra 仍是子工作流的执行引擎，项目级总编排由 PGlite + 调度器承担。

Phase 4：暂停、恢复、取消与审批

  • 项目级暂停/恢复 API 和 Overview 操作按钮；
  • 暂停时新节点停止派发，运行中实验支持软暂停/取消选择；
  • 审批节点接入现有 approvalGateWorkflow。
  • 定期总结支持用户配置时间间隔，到点后自动生成并投递到 项目概述 -> 定期总结。

Phase 5：并行实验矩阵与并行论文

  • 本方法实现 下的实验矩阵支持同时运行多个实验；
  • 学术论文撰写 支持多个章节并行生成；
  • 支持 partial 状态、章节合并、引用核验和失败回退。

验收标准

  • 用同一个演示项目真实运行 5 个并行实验，Overview 图能同时显示 5 个 running；
  • 项目暂停后没有新节点被派发，恢复后自动继续；
  • 一个实验失败但达到阈值时，项目进入 partial 而不是整体失败；
  • 论文多个章节并行生成后能合并并进入人工审查；
  • 服务重启后，等待中、审批中、运行中的节点都能恢复；
  • 四语言、四主题下 Overview 执行图均可读、无重叠、可交互。

6. 需要你确认的设计决策

  1. 执行图是否放在 项目概述 -> 进度与待决策 页面，还是单独新增一个 Overview 主区域图表？
  2. 是否每个项目只允许一个当前执行实例，还是允许“重新开启上一轮执行”的版本化历史？
  3. 暂停时运行中的实验默认“跑到安全检查点后暂停”，还是“立即取消”？
  4. 并行实验的默认失败策略是否采用“达到阈值即可继续”，而不是“一个失败就整体失败”？
  5. 默认并发上限是全局统一配置，还是每个项目单独配置？

如果第 1 节那张巨型图符合你的预期，下一步就可以按 Phase 1 先做数据模型和 Overview 执行图。
